Legal Entities — CKYC Verification: Display Variants

All variants explore how CKYC (Central KYC) status is surfaced in the entity onboarding admin view on C2treds.
CKYC is a CERSAI-operated registry. TReDS platforms must verify it for all legal entity participants (Buyers, Suppliers, Financiers).
Each variant changes only the CKYC column/cell treatment — entity identity columns remain constant.

Variant 6 — Entity Type × CKYC Requirement Matrix CONTEXT-AWARE CKYC requirements differ per entity type in India. This variant makes the platform aware of that — it only requires CKYC where mandated.
Entity Type CKYC Required? Key Identifiers CKYC Fetch Logic If Not Found Example Status Display
Pvt. Ltd. ✓ Required PAN + CIN Auto-fetch on PAN submission. Retry after 24h if failed. Block onboarding until resolved or manual override approved. Verified
Pub. Ltd. ✓ Required PAN + CIN Auto-fetch on PAN submission. Additional directors' KYC may be required by financiers. Block onboarding until resolved or manual override approved. Mismatch
LLP ✓ Required PAN + LLPIN Fetch by PAN. LLPIN used for secondary verification of designated partners. Block onboarding. LLPs are newer entities; CKYC gaps are more common — escalate to compliance team. Not Found
Partnership ✓ Required
Partners' individual CKYC also required
 Firm PAN + Partner PANs Fetch firm CKYC + each partner's CKYC. All must be Verified to proceed. Partial block — if firm CKYC found but a partner's CKYC is missing, flag the specific partner. Partial
Proprietorship ✓ Required
Individual CKYC of proprietor
 Proprietor PAN Fetch individual CKYC for proprietor. No separate firm CKYC entity in registry. Proprietors often lack CKYC. Fallback: accept Aadhaar-based eKYC or physical KYC documents. Fallback KYC
Design principle: The CKYC column meaning changes by entity type. A "Not Found" for an LLP is a compliance blocker requiring escalation. A "Not Found" for a proprietorship triggers a different fallback flow (eKYC/physical KYC). The platform should encode this logic so the admin sees the right action, not just the status. This matrix is the decision tree behind all the preceding variants.
Decision Guide — Which Variant to Use Where SUMMARY
Context Recommended Variant Reason
Entity list (50+ rows, all statuses) V1 — Pill Compact. Pre-attentive colour. Filter by status to drill down.
Entity detail page (single entity review) V2 — Verification Card Full field-level comparison visible. Admin can act without switching context.
Onboarding queue (admin-triggered fetch) V3 — Action State Makes the async fetch operation visible. Fetch button + loading state prevents confusion.
Mixed list (most Verified, few flagged) V4 — Expandable Compact scan for the majority; rich detail on demand for flagged rows only.
"Requires Attention" filtered view V5 — Error Cards Every row is a problem; contextual guidance embedded means admin can resolve without help docs.
